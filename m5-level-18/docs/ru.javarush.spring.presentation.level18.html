Уровень 18: OAuth2 и JWT для микросервисов

Мы переходим от классической безопасности на основе сессий к современному stateless-подходу, который является стандартом для REST API и микросервисной архитектуры. Вы познакомитесь с двумя фундаментальными технологиями: OAuth2, фреймворком для делегированной авторизации, и JSON Web Tokens (JWT), стандартом для создания безопасных токенов доступа.

Мы разберем структуру JWT, поймем, как цифровая подпись гарантирует его целостность, и реализуем полный цикл stateless-аутентификации в Spring Security. Вы научитесь создавать собственный фильтр для обработки токенов и поймете, зачем нужны Refresh-токены.

Stateful vs. Stateless

Давайте вспомним, почему сессии (stateful-подход) плохо подходят для микросервисов:

  1. Если вы запускаете несколько экземпляров одного сервиса, вам нужна сложная и дорогая репликация сессий между ними, иначе пользователь будет "разлогиниваться" при каждом запросе, попадающем на новый экземпляр. Проблема масштабирования.
  2. Клиент "привязан" к сессии на сервере.
  3. Традиционные сессии на основе cookie плохо работают с клиентами, которые не являются браузерами (например, мобильные приложения, другие микросервисы).

Stateless-подход решает эти проблемы. Сервер не хранит состояние аутентификации. Вместо этого клиент при каждом запросе предоставляет самодостаточный токен, который содержит всю необходимую информацию для его аутентификации и авторизации.

Эта диаграмма сравнивает stateful-архитектуру (с общей базой сессий) и stateless-архитектуру (с JWT-токенами), наглядно демонстрируя, как stateless-подход упрощает масштабирование и повышает отказоустойчивость.

Что такое OAuth2?

OAuth2 — это открытый фреймворк авторизации. Важно понимать его основную цель.

OAuth2 — это не про аутентификацию (проверку личности пользователя). Это про делегирование доступа. Он предоставляет приложениям ("клиентам") ограниченный доступ к ресурсам пользователя на HTTP-сервисе без необходимости передавать приложению логин и пароль пользователя.

Когда вы нажимаете "Войти с помощью Google" на каком-либо сайте, этот сайт (клиент) не получает ваш пароль от Google. Вместо этого вы (владелец ресурса) даете сайту разрешение (в виде токена) получить доступ к вашему имени и email-адресу (ресурсам) на серверах Google.

Роли в OAuth2

Фреймворк OAuth2 определяет четыре основные роли:

  • Resource Owner это вы, пользователь. Вы владеете своими данными и можете давать разрешения на доступ к ним.
  • Client приложение, которое хочет получить доступ к ресурсам владельца.
  • Authorization Server сервер, который аутентифицирует владельца ресурса и выдает клиенту токены доступа (Access Tokens) после получения согласия. Это "вышибала", который проверяет пропуски.
  • Resource Server сервер, на котором хранятся защищенные ресурсы. Он доверяет токенам, выданным сервером авторизации, и предоставляет доступ к данным, если клиент предъявил валидный токен.

Что такое JWT?

Хотя OAuth2 не предписывает конкретный формат токенов, стандартом де-факто для их реализации стал JWT (JSON Web Token).

JWT — это открытый стандарт (RFC 7519), который определяет компактный и самодостаточный способ для безопасной передачи информации между сторонами в виде JSON-объекта.

"Самодостаточный" — ключевое слово. Вся необходимая информация (кто пользователь, какие у него права, до какого времени токен действителен) находится внутри самого токена.

"Безопасный" — потому что JWT может быть цифровым образом подписан. Это гарантирует, что токен не был подделан или изменен в пути.

Структура JWT

JWT выглядит как длинная строка, состоящая из трех частей, разделенных точками: xxxxx.yyyyy.zzzzz

Каждая из первых двух частей — это JSON, закодированный в Base64Url. Их легко раскодировать, поэтому в них нельзя хранить секреты. Секретность обеспечивает только третья часть — подпись.

Payload (Claims)

Payload — это сердце токена. Он содержит утверждения (claims) — информацию о пользователе и метаданные токена.

Существует три типа claims:

  • Registered (Стандартные), предопределенные, но необязательные.
    • sub (Subject): идентификатор пользователя.
    • exp (Expiration Time): время, когда токен "протухнет" (в формате Unix timestamp).
    • iat (Issued At): время, когда токен был выдан.
  • Public (Публичные): могут быть любыми, но их имена должны быть уникальными, чтобы избежать коллизий (часто используют URI).
  • Private (Приватные): кастомные утверждения, о которых договорились клиент и сервер. Самое частое применение — передача ролей и прав доступа.
    • roles: ["USER", "MODERATOR"]
    • permissions: ["READ_POSTS", "CREATE_COMMENTS"]

Signature

Подпись — это то, что делает JWT безопасным. Она гарантирует целостность токена.

Как она создается:

  1. Берутся закодированные заголовок и полезная нагрузка.
  2. Они объединяются через точку.
  3. Полученная строка хэшируется с использованием алгоритма, указанного в заголовке (alg), и секретного ключа, который известен только серверу.

Когда сервер получает токен, он повторяет эту операцию. Если сгенерированная им подпись совпадает с той, что в токене, значит, токен подлинный и его payload не был изменен. Если подписи не совпадают — токен подделан и должен быть отвергнут.

Обратите внимание: после выдачи токена Сервер Ресурсов не обращается к Серверу Авторизации. Он может проверить токен самостоятельно, зная секретный ключ.

Реализация в Spring Security

Чтобы переключить Spring Security в stateless-режим, нужно:

  1. Отключить управление сессиями: http.sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
  2. Отключить CSRF-защиту: http.csrf(AbstractHttpConfigurer::disable). CSRF — это атака на сессии, в stateless-режиме она нерелевантна.
  3. Отключить стандартную форму входа: Она работает с сессиями. Вместо нее мы создадим свой эндпоинт для логина.
  4. Добавить свой фильтр для проверки JWT.
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(AbstractHttpConfigurer::disable)
        .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll() // Эндпоинты для логина/регистрации
            .anyRequest().authenticated()
        )
        // Добавляем наш фильтр перед стандартным фильтром аутентификации
        .addFilterBefore(jwtAuthenticationFilter(), UsernamePasswordAuthenticationFilter.class);

    return http.build();
}

Кастомный фильтр для JWT

Нам нужно создать свой фильтр, который будет выполняться для каждого запроса.

Логика фильтра:

public class JwtAuthenticationFilter extends OncePerRequestFilter {
    // ...

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain) {
        // 1. Получить токен из заголовка Authorization
        String token = extractTokenFrom(request);
        if (token == null) {
            chain.doFilter(request, response); // Если токена нет, идем дальше
            return;
        }

        // 2. Провалидировать токен (проверить подпись и срок действия)
        if (jwtTokenProvider.validateToken(token)) {
            // 3. Если токен валиден, получить из него username и роли
            String username = jwtTokenProvider.getUsername(token);
            List<GrantedAuthority> authorities = jwtTokenProvider.getAuthorities(token);

            // 4. Создать объект Authentication и положить его в SecurityContext
            Authentication auth = new UsernamePasswordAuthenticationToken(username, null, authorities);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        chain.doFilter(request, response); // Передаем запрос дальше по цепочке
    }
}

После этого SecurityContext будет "заполнен", и @PreAuthorize сможет работать так же, как и в stateful-режиме.

Refresh токены

Access Token (JWT) содержит права доступа и его нельзя отозвать. Если его украдут, злоумышленник сможет использовать его до истечения срока действия (exp).

Поэтому Access Token'ы делают короткоживущими (5-15 минут). Но заставлять пользователя логиниться каждые 5 минут — плохой UX.

Можно использовать пару токенов.

  • Access Token: короткоживущий, используется для доступа к ресурсам.
  • Refresh Token: долгоживущий (дни, недели), хранится в безопасном месте. Его единственная цель — получить новый Access Token.

Когда Access Token "протухает", клиент идет со своим Refresh Token'ом на специальный эндпоинт /api/auth/refresh. Сервер авторизации проверяет Refresh Token, и если он валиден, выпускает новую пару Access и Refresh токенов. Это позволяет реализовать сессии "помнить меня", не жертвуя безопасностью.

Поток обновления с Refresh Token

Эта диаграмма иллюстрирует механизм обновления токенов: когда короткоживущий Access Token истекает, клиент использует долгоживущий Refresh Token для безболезненного получения новой пары токенов без необходимости повторного ввода пароля.

JWT в микросервисах

JWT идеально подходит для микросервисной архитектуры.

  1. Существует отдельный Сервер Авторизации, который отвечает за аутентификацию и выпуск JWT.
  2. Клиент получает токен и прикладывает его к запросам ко всем остальным микросервисам.
  3. Каждый микросервис (Сервер Ресурсов) может самостоятельно проверить подпись токена.

Для этого все сервисы должны знать публичный ключ (если используется асимметричное шифрование RSA) или общий секретный ключ (если используется симметричный HMAC) Сервера Авторизации.

Это устраняет "бутылочное горлышко": сервисам не нужно при каждом запросе обращаться к Серверу Авторизации для валидации токена.

Защита ресурсов

После того как наш JWT-фильтр успешно аутентифицировал пользователя и поместил его данные в SecurityContext, мы можем использовать метод-уровневую безопасность точно так же, как и раньше.

@PreAuthorize может получить доступ к информации, которую мы "зашили" в токен.

В JWT Payload: { "sub": "john.doe", "roles": ["USER"], "department": "SALES" }

В коде микросервиса:

@Service
public class ReportService {

    // Доступ разрешен, только если у пользователя в токене есть роль 'ADMIN'
    // ИЛИ если department в токене совпадает с аргументом метода.
    @PreAuthorize("hasRole('ADMIN') or authentication.principal.claims['department'] == #department")
    public Report generateReportForDepartment(String department) {
        // ...
    }
}

Это позволяет реализовать очень гибкие и гранулярные правила авторизации, основанные на данных из токена.

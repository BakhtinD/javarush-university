Уровень 17: Spring Security — основы безопасности

Мы научились создавать сложные приложения(но это не точно), но до сих пор они были незащищенными. На этом уровне мы закроем эту брешь, изучив Spring Security — мощнейший фреймворк для обеспечения безопасности в Java-приложениях. Вы поймете фундаментальную разницу между аутентификацией и авторизацией.

Разберем архитектуру Spring Security, основанную на цепочке фильтров, и научимся настраивать ее с помощью современного подхода. Вы узнаете, как загружать данные о пользователях из базы данных, и, что самое важное, как безопасно хранить их пароли с использованием BCrypt.

Почему безопасность важна?

В любом реальном приложении есть данные или действия, которые доступны не всем. Искушение написать простую проверку if (user.getRole().equals("ADMIN")) велико, но это крайне опасно.

Веб-приложения подвержены десяткам угроз:

  • Межсайтовый скриптинг (XSS)
  • Подделка межсайтовых запросов (CSRF)
  • SQL-инъекции
  • Утечка паролей пользователей

Spring Security — это не просто библиотека для проверки логина и пароля. Это комплексный фреймворк, который предоставляет защиту от большинства распространенных атак "из коробки". Игнорировать его — значит оставлять свое приложение беззащитным.

Аутентификация vs. Авторизация

Это два столпа, на которых строится любая система безопасности. Крайне важно понимать разницу.

  • Аутентификация (Authentication) процесс проверки личности. Система отвечает на вопрос: "Кто ты?".

    • Примеры: ввод логина и пароля, использование биометрии, предъявление паспорта.
    • Результат: система либо подтверждает вашу личность, либо нет.

  • Авторизация (Authorization) процесс проверки прав доступа. После успешной аутентификации система отвечает на вопрос: "Что тебе можно делать?".

    • Примеры: проверка, имеет ли пользователь право читать этот документ, удалять этот комментарий или заходить в админ-панель.
    • Результат: доступ разрешен или запрещен.

Аутентификация — это ваш пропуск в здание. Авторизация — это проверка, дает ли этот пропуск вам право войти в конкретный кабинет.

Архитектура

Spring Security построен на концепции цепочки сервлетных фильтров (Servlet Filter Chain).

Вместо того чтобы запрос сразу попадал в ваш контроллер, он сначала проходит через ряд фильтров Spring Security. Каждый фильтр отвечает за свою небольшую часть безопасности.

  • Один фильтр проверяет CSRF-токен.
  • Другой — "извлекает" пользователя из сессии.
  • Третий (UsernamePasswordAuthenticationFilter) — обрабатывает логин и пароль из формы.
  • Четвертый (AuthorizationFilter) — проверяет, есть ли у пользователя права на доступ к запрошенному URL.

Только если запрос успешно прошел всю цепочку, он будет передан в DispatcherServlet и ваш контроллер.

Быстрый старт

Магия Spring Boot в действии. Чтобы включить базовую защиту, достаточно добавить одну зависимость в pom.xml:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Что произойдет после этого?

  1. Все эндпоинты вашего приложения станут защищенными по умолчанию.
  2. Spring Boot автоматически сгенерирует пароль для пользователя user и выведет его в консоль при старте.
  3. При попытке доступа к любому URL вы будете перенаправлены на стандартную страницу входа.
  4. Будет включена HTTP Basic аутентификация для API-клиентов.

Хорошо, но для реального приложения нам нужна своя конфигурация.

Современная конфигурация

Раньше для настройки Spring Security наследовались от класса WebSecurityConfigurerAdapter. Этот подход устарел (deprecated).

Современный способ — это создание @Configuration класса, в котором вы определяете бин типа SecurityFilterChain.

@Configuration
@EnableWebSecurity // Включает веб-безопасность Spring
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        // Здесь мы настраиваем цепочку фильтров с помощью удобного Lambda DSL
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**", "/login").permitAll() // Разрешить доступ к этим URL всем
                .requestMatchers("/admin/**").hasRole("ADMIN") // Только для админов
                .anyRequest().authenticated() // Все остальные запросы требуют аутентификации
            )
            .formLogin(Customizer.withDefaults()); // Включить стандартную форму входа

        return http.build();
    }
}

AuthenticationManager и UserDetailsService

Как Spring Security узнает, правильный ли пароль ввел пользователь?

В центре процесса аутентификации стоит AuthenticationManager. Он получает "токен аутентификации" (например, с логином и паролем) и должен решить, валиден ли он.

AuthenticationManager делегирует загрузку данных о пользователе специальному интерфейсу — UserDetailsService.

UserDetailsService имеет всего один метод: UserDetails loadUserByUsername(String username) throws UsernameNotFoundException;

Его задача — по имени пользователя найти его данные (включая хэш пароля и роли) и вернуть их в виде объекта UserDetails.

Последовательность проверки безопасности

Эта диаграмма иллюстрирует последовательный процесс обеспечения безопасности: сначала система проверяет, кто вы (Аутентификация), и только в случае успеха определяет, что вам разрешено делать (Авторизация).

Хранение пользователей в БД

Наша задача — реализовать UserDetailsService, который будет "ходить" в БД.

@Service // Это обычный Spring-компонент
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;
    // ... конструктор с @Autowired ...

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        // 1. Находим нашего пользователя в БД
        User user = userRepository.findByUsername(username)
            .orElseThrow(() -> new UsernameNotFoundException("User not found: " + username));

        // 2. Создаем и возвращаем объект UserDetails, который понимает Spring Security
        return new org.springframework.security.core.userdetails.User(
            user.getUsername(),
            user.getPassword(), // Здесь должен быть хэшированный пароль!
            // Преобразуем наши роли в GrantedAuthority
            user.getRoles().stream()
                .map(role -> new SimpleGrantedAuthority(role.getName()))
                .collect(Collectors.toList())
        );
    }
}

Шифрование паролей

НИКОГДА, НИКОГДА, НИКОГДА не храните пароли в базе данных в открытом виде или с использованием слабых алгоритмов хэширования (MD5, SHA-1).

Spring Security предоставляет интерфейс PasswordEncoder для безопасного хэширования паролей. Стандартная и рекомендуемая реализация — BCryptPasswordEncoder.

BCrypt — это адаптивный алгоритм. Он не только хэширует пароль, но и добавляет к нему случайную "соль" (salt), а также позволяет настроить "сложность" (work factor), чтобы хэширование занимало определенное время, делая перебор паролей (brute-force) очень медленным.

Вы должны объявить бин PasswordEncoder в вашей конфигурации:

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

При регистрации пользователя вы используете passwordEncoder.encode(rawPassword) для получения хэша.

Конфигурация авторизации

Авторизация — это настройка правил доступа. Основной способ — использование Lambda DSL в бине SecurityFilterChain.

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            // Правила применяются по порядку, от более конкретных к более общим
            .requestMatchers("/css/**", "/js/**").permitAll() // Статические ресурсы доступны всем
            .requestMatchers("/admin/**").hasRole("ADMIN") // URL для админов
            .requestMatchers("/profile/**").hasAnyRole("USER", "ADMIN") // Для пользователей и админов
            .requestMatchers("/api/public/**").permitAll()
            .anyRequest().authenticated() // Все остальные URL требуют входа
        );
        // ... другие настройки ...
    return http.build();
}

hasRole("ADMIN") на самом деле проверяет наличие полномочия ROLE_ADMIN.

Метод-уровневая безопасность

Иногда правила доступа зависят не от URL, а от сложной бизнес-логики (например, "редактировать пост может только его автор или админ"). Описывать такие правила через URL неудобно.

Для этого существует метод-уровневая безопасность.

  1. Включаем ее в конфигурации: @EnableMethodSecurity.
  2. Используем аннотации прямо на методах ваших сервисов.
@Service
public class PostService {

    @PreAuthorize("hasRole('ADMIN') or #post.author.username == authentication.name")
    public void editPost(Post post, PostUpdateDto data) {
        // ... логика редактирования ...
    }

    @PreAuthorize("hasRole('ADMIN')")
    public void deletePost(Long postId) {
        // ... логика удаления ...
    }
}

@PreAuthorize использует мощный язык выражений SpEL (Spring Expression Language), который дает доступ к текущему пользователю (authentication), аргументам метода и т.д.

Роли и полномочия (Authorities)

В Spring Security фундаментальным понятием является GrantedAuthority (полномочие). Это единичное право, которое может быть предоставлено пользователю.

Роль — это просто соглашение. По умолчанию, Spring Security считает, что роль — это GrantedAuthority, имя которой начинается с префикса ROLE_.

Выражение hasRole("ADMIN") — это всего лишь сокращение для hasAuthority("ROLE_ADMIN").

Вы можете использовать чистые Authorities без ролей, если ваша модель доступа более гранулярная. .requestMatchers("/posts/delete").hasAuthority("CAN_DELETE_POSTS")

Управление сессиями

После успешной аутентификации Spring Security по умолчанию начинает управлять HTTP-сессией.

  1. Создается объект Authentication, содержащий информацию о пользователе (имя, роли).
  2. Этот объект помещается в SecurityContext, который, в свою очередь, хранится в HTTP-сессии на сервере.
  3. Сервер отправляет клиенту (браузеру) cookie с идентификатором сессии, обычно JSESSIONID.
  4. При каждом последующем запросе браузер автоматически отправляет эту cookie. Spring Security находит сессию по ID, извлекает SecurityContext и "узнает" пользователя.

Этот механизм называется stateful, так как сервер хранит состояние (сессию) для каждого клиента.

Stateless Security

Stateful-подход с сессиями отлично работает для традиционных веб-приложений (монолитов).

Однако в мире микросервисов и современных фронтендов (React, Angular) предпочтителен stateless-подход.

Если у вас 10 экземпляров одного сервиса, запрос может попасть на любой из них. Как они будут делить одну сессию? (Требуется сложная репликация сессий).

Не хранить состояние на сервере вообще. Вместо JSESSIONID, сервер после логина выдает клиенту токен. Клиент должен прикладывать этот токен к каждому запросу. Сервер проверяет валидность токена при каждом запросе, не обращаясь к сессии.

Этот подход мы подробно изучим на следующем уровне.

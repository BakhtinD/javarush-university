Уровень 15: Введение в GraphQL

До сих пор мы рассматривали REST как основной способ построения API. На этом уровне мы изучим его мощную и гибкую альтернативу — GraphQL. Вы узнаете, почему технологии, разработанные в Facebook, завоевали мир, и как они решают классические проблемы REST, такие как избыточная (over-fetching) и недостаточная (under-fetching) выборка данных.

Сегодня разберем три кита GraphQL: Queries, Mutations и Subscriptions. Вы научитесь определять схему API, которая служит строгим контрактом между клиентом и сервером, и связывать ее с вашим Java-кодом с помощью Spring for GraphQL. Мы также затронем роль GraphQL в микросервисной архитектуре и обсудим, как решать проблему производительности N+1 с помощью паттерна DataLoader.

Проблемы REST API

Несмотря на свою популярность, REST имеет ограничения, которые особенно заметны в сложных системах с разнообразными клиентами (веб, мобильные, десктоп).

  • Over-fetching (избыточная выборка) получаете больше данных, чем вам нужно.
    • Пример: Вам нужно только имя пользователя, но эндпоинт GET /users/{id} возвращает объект User с 20 полями. Это лишний трафик и ненужная работа для сервера.
  • Under-fetching (недостаточная выборка) получаете недостаточно данных и вынуждены делать дополнительные запросы.
    • Чтобы показать страницу профиля, вам нужно сделать один запрос на GET /users/{id}, второй на GET /users/{id}/posts и третий на GET /users/{id}/followers. Это замедляет загрузку.

Клиент жестко привязан к структуре данных, которую диктует сервер.

Что такое GraphQL?

GraphQL — это язык запросов для API и среда выполнения на стороне сервера для обработки этих запросов.

Это не фреймворк и не база данных, а спецификация, разработанная Facebook.

Вместо того чтобы сервер определял, какие данные возвращать, клиент в своем запросе точно описывает, какие данные ему нужны, включая вложенные связи. Сервер гарантирует, что вернет данные именно в той структуре, в которой их запросил клиент, и ничего лишнего.

GraphQL переворачивает отношения: теперь не сервер, а клиент диктует "контракт" данных.

Основные концепции

GraphQL API строится на трех основных типах операций:

  1. Query — операция для чтения данных. Аналог GET в REST.
  2. Mutation — операция для изменения данных (создание, обновление, удаление). Аналог POST, PUT, DELETE.
  3. Subscription — операция для поддержания долговременного соединения с сервером. Позволяет клиенту получать обновления данных в реальном времени, когда они происходят на сервере (обычно через WebSockets).

Схема и типы

Схема — это сердце любого GraphQL API. Она служит строгим контрактом, который описывает все возможности API. Схема пишется на специальном языке — Schema Definition Language (SDL).

Схема определяет:

  • Какие типы данных существуют (User, Post).
  • Какие запросы (queries) можно выполнять.
  • Какие мутации доступны.
# Схема определяет тип "Книга" с полями
type Book {
    id: ID!
    title: String!
    author: Author
}

# Схема определяет тип "Автор"
type Author {
    id: ID!
    name: String!
    books: [Book]
}

# Корневой тип для всех запросов на чтение
type Query {
    bookById(id: ID!): Book
    allAuthors: [Author]
}

! означает, что поле является обязательным (non-nullable).

Запросы

Клиент формирует запрос, структура которого "зеркалит" структуру типов в схеме.

Пример запроса: "Дай мне книгу с id=1, мне нужно ее название и имя ее автора".

query GetBookAndAuthorName {
  bookById(id: "1") {
    title
    author {
      name
    }
  }
}

Ответ от сервера (JSON):

{
  "data": {
    "bookById": {
      "title": "The Great Gatsby",
      "author": {
        "name": "F. Scott Fitzgerald"
      }
    }
  }
}

Ответ в точности повторяет структуру запроса. Никаких лишних полей.

Мутации

Мутации используются для изменения данных. Синтаксис похож на запросы, но они должны начинаться с ключевого слова mutation.

Определение мутации в схеме:

type Mutation {
    addBook(title: String!, authorId: ID!): Book
}

Выполнение мутации клиентом:

mutation CreateBook {
  addBook(title: "New Book", authorId: "2") {
    id
    title
  }
}

Как и в случае с запросами, после выполнения мутации можно запросить определенные поля созданного или измененного объекта.

Spring for GraphQL

Spring for GraphQL — это официальный проект от команды Spring, который упрощает создание GraphQL-серверов.

Ключевая зависимость, которую нужно добавить в pom.xml:

<dependency>
<groupId>org.springframework.boot</groupId>
<artifactId>spring-boot-starter-graphql</artifactId>
</dependency>

Этот стартер автоматически:

  • Подключает библиотеку GraphQL Java — ядро любого GraphQL-сервера на Java.
  • Настраивает эндпоинт /graphql.
  • Настраивает поддержку WebSockets для подписок.
  • Ищет файлы со схемой в вашем проекте.

Создание схемы

По соглашению, Spring for GraphQL ищет файлы с описанием схемы в директории: src/main/resources/graphql/

Вы можете создать один большой файл schema.graphqls или разбить схему на несколько файлов (book.graphqls, author.graphqls). Spring автоматически найдет и объединит их все в одну общую схему.

src/main/resources/graphql/book.graphqls:

type Query {
    bookById(id: ID!): Book
}

type Book {
    id: ID!
    title: String!
}

Контроллер и маппинг

Spring for GraphQL использует аннотации, очень похожие на Spring MVC, для связывания полей схемы с методами вашего Java-кода.

Контроллер помечается стандартной аннотацией @Controller.

@Controller
public class BookController {

    private final BookService bookService;
    // ... конструктор ...

    // Этот метод будет обрабатывать поле "bookById" из типа "Query"
    @QueryMapping
    public Book bookById(@Argument Long id) {
        // @Argument связывает аргумент из GraphQL-запроса с параметром метода
        return bookService.findById(id);
    }

    // Этот метод будет обрабатывать мутацию "addBook"
    @MutationMapping
    public Book addBook(@Argument String title, @Argument Long authorId) {
        return bookService.create(title, authorId);
    }
}

Data Fetchers

По сути, каждый метод, помеченный @QueryMapping, @MutationMapping или @SchemaMapping (для полей вложенных объектов), является "получателем данных" (Data Fetcher).

Data Fetcher — это кусочек кода, который отвечает за возврат данных для одного конкретного поля в вашей схеме.

Когда GraphQL Java получает запрос, он парсит его и для каждого запрашиваемого поля вызывает соответствующий Data Fetcher. Spring for GraphQL просто предоставляет удобный способ объявлять эти фетчеры с помощью аннотаций.

GraphQL в микросервисах

GraphQL редко используется для внутрисервисного общения. Его основная сила проявляется на "границе" системы, как точка входа для клиентов.

Частый паттерн — GraphQL Gateway или Backend for Frontend (BFF).

  • Создается отдельный GraphQL-сервис, который является единой точкой входа для всех фронтенд-приложений.
  • Этот сервис сам не имеет своей базы данных и бизнес-логики.
  • Его Data Fetcher'ы ходят по сети в другие, "внутренние" микросервисы (по REST или gRPC), собирают от них данные и объединяют их в один GraphQL-ответ.

Это позволяет фронтенду получать все необходимые данные одним запросом, при этом сохраняя независимость и декомпозицию на бэкенде.

Схема наглядно показывает роль GraphQL как "фасада", который скрывает сложность внутренней микросервисной архитектуры от клиента.

Проблема N+1 в GraphQL

Гибкость GraphQL может легко привести к серьезным проблемам с производительностью.

Схема: type Author { books: [Book] }

Запрос:

{
  allAuthors {
    name
    books {
      title
    }
  }
}

Наивная реализация на сервере:

  1. Выполнить 1 SQL-запрос, чтобы получить всех авторов.
  2. Затем для каждого из N авторов выполнить еще по одному SQL-запросу, чтобы получить его книги.

Итог: 1 + N запросов к базе данных, что катастрофически неэффективно.

Решение с помощью DataLoaders

DataLoader — это стандартный паттерн в мире GraphQL для решения проблемы N+1. Это не магия, а простая утилита для пакетирования (batching) и кэширования запросов в рамках одного GraphQL-запроса.

Как это работает:

  1. Когда резолверы запрашивают книги для авторов с ID 1, 5 и 10, эти запросы не выполняются немедленно. Они накапливаются в DataLoader.
  2. В определенный момент DataLoader "выстреливает", собирает все уникальные ID (1, 5, 10) и выполняет один SQL-запрос: SELECT * FROM books WHERE author_id IN (1, 5, 10).
  3. Получив результат, он распределяет его по соответствующим запросам.

Spring for GraphQL имеет встроенную поддержку этого механизма.

Обработка ошибок

В REST мы привыкли использовать HTTP-статусы (404, 400, 500) для сообщения об ошибках.

GraphQL подходит к этому иначе. Даже если при обработке поля произошла ошибка, сервер чаще всего вернет HTTP статус 200 OK.

Тело ответа будет содержать два поля: data (которое может быть null или содержать частично успешные результаты) и errors.

Пример ответа с ошибкой:

{
  "data": {
    "bookById": null
  },
  "errors": [
    {
      "message": "Book with ID 999 not found",
      "locations": [ { "line": 2, "column": 3 } ],
      "path": [ "bookById" ],
      "extensions": {
        "classification": "DataFetchingException"
      }
    }
  ]
}

Это позволяет клиенту получить как успешно извлеченные данные, так и информацию об ошибках в рамках одного ответа.
